# Dreamskills 设计思路与架构

> 本文档回答三个问题：Dreamskills **从哪些上游项目取了什么长**、**为什么这样整合**、**整体架构如何运转**。
> 上游分析基于 GitHub 高星仓库实测调研（obra/superpowers、anthropics/skills、github/spec-kit、Fission-AI/OpenSpec、nextlevelbuilder/ui-ux-pro-max-skill、Leonxlnx/taste-skill、Nutlope/hallmark、addyosmani/web-quality-skills、amElnagdy/guard-skills、microsoft/waza、bmad-code-org/BMAD-METHOD 等）。

---

## 1. 整合矩阵：谁的长处，进了哪里

### 1.1 规格驱动层（来自 OpenSpec + Spec-Kit）

| 上游优势 | 采纳 | 裁剪理由 |
|---|---|---|
| OpenSpec：`changes/` 文件夹 + delta specs（ADDED/MODIFIED/REMOVED）+ archive 归档 | ✅ 全盘采纳 | "规格层的 Git"思想是 brownfield 与团队协作的最佳实践，纯 Markdown 零依赖 |
| OpenSpec：契约先行、人先审提案再写代码 | ✅ 采纳 | AI 写规格、人审提案，是防止方向性返工的第一道闸 |
| OpenSpec：fluid not rigid（无刚性阶段门禁） | ✅ 采纳 | 刚性门禁在频繁迭代中被证实是最大摩擦源 |
| Spec-Kit：九条宪法、Simplicity Gate | ✅ 轻量采纳（压缩为 6 条 + 复杂度门） | 九条宪法对个人/中小项目过重；保留"库优先、测试先行、反抽象"三条精华 |
| Spec-Kit：`[NEEDS CLARIFICATION]` 强制标记歧义 | ✅ 采纳 | 这是防 AI 幻觉猜测的最有效 prompt 工程 |
| Spec-Kit：CLI（Python/uv 安装）、bundles/extensions | ❌ 不采纳 | 违背"轻量零依赖"设计目标，技能包不应要求特定运行时 |

### 1.2 开发纪律层（来自 Superpowers + BMAD）

| 上游优势 | 采纳 | 裁剪理由 |
|---|---|---|
| Superpowers：7 步流水线（brainstorm → worktree → plan → implement → TDD → review → finish） | ✅ 采纳为主干 | 全流程编排完整性在同类项目中最强 |
| Superpowers：强制技能触发（hooks 注入元规则，mandatory not suggestions） | ✅ 采纳 | 会话启动注入"先查技能再动手"，是把流程从建议变成纪律的关键机制 |
| Superpowers：2-5 分钟粒度任务 + 子代理两阶段审查（spec 合规 → 代码质量） | ✅ 采纳 | 粒度控制是防止 AI 跑偏的最有效手段 |
| Superpowers：TDD 强制、Evidence over claims | ✅ 采纳 | 完成即验证，杜绝"看起来做完了" |
| Superpowers：不接受外部技能贡献（封闭） | ❌ 反向改进 | Dreamskills 提供 dream-write-skill 元技能，鼓励扩展 |
| BMAD：决策显式化（briefs/specs/architecture 向后传递） | ✅ 采纳 | 把隐含假设写成显式决策，避免每轮对话重复解释 |
| BMAD：人类保留判断权（without handing over judgment） | ✅ 采纳 | 所有门禁是"提示人确认"，不是自动放行 |

### 1.3 UI 美学层（来自 UI UX Pro Max + Taste + Hallmark）

| 上游优势 | 采纳 | 裁剪理由 |
|---|---|---|
| UI UX Pro Max：全量数据资产（styles/products/colors/typography/charts/icons/ui-reasoning/ux-guidelines/motion/landing/app-interface/react-performance/google-fonts + 22 技术栈 CSV） | ✅ 全量整合（v2，见 ADR-004） | CSV 是纯文件不构成运行时依赖；保真上游全部要素 |
| UI UX Pro Max：BM25 检索 + 设计系统生成脚本（search.py/core.py/design_system.py） | ✅ 全量整合（可选路径） | 需 Python 3（标准库）；无 Python 时走 CSV 直读降级路径 |
| UI UX Pro Max：优先级规则表（10 级）、4 步工作流、技术栈检测（绝不假设）、0 结果禁止编造、MASTER+Overrides 持久化 | ✅ 全盘采纳 | 这是"数据驱动设计"的方法论骨架 |
| UI UX Pro Max：8 个子能力（logo/CIP/icon/banner/social-photos/slides/brand/design-system+ui-styling） | ✅ 全盘采纳（合并为 references） | design（视觉资产）、design-system（token）、ui-styling（shadcn/Tailwind）、brand、banner-design、slides、stack 审计全部整合进 dream-ui |
| UI UX Pro Max：7 阶段设计审计 + design-review 报告格式 | ✅ 全盘采纳 | 补齐"做完必须查"的视觉验证闭环 |
| Taste-Skill：DESIGN_VARIANCE / MOTION_INTENSITY / VISUAL_DENSITY 三旋钮 | ✅ 采纳（与上游 --variance/--motion/--density 滑杆合并） | 两套滑杆语义一致，统一为一套 |
| Taste-Skill：硬性 em-dash 禁令、canonical 代码骨架 | ✅ 采纳 | 硬规则对反 AI 味立竿见影 |
| Hallmark：57 道 slop 测试门 + 生成前自我批判 | ✅ 精简为 40 门 | 57 门全量对单次生成 token 压力大；40 门覆盖全部高风险项 |
| Hallmark：macrostructure 先行（先骨架后主题，防同模板换色） | ✅ 采纳 | 反"同一模板换色"的指纹化思想核心 |
| Web-Quality：Lighthouse/CWV/WCAG 数值阈值 | ✅ 移入 dream-verify | 归属验证层而非美学层，职责分离 |

### 1.5 需求澄清与上下文层（来自 Product-Manager-Skills + ProductSpec + planning-with-files + pro-workflow + caveman）

| 上游优势 | 采纳 | 裁剪理由 |
|---|---|---|
| Product-Manager-Skills：Adaptive Decision Ladder（先问 3-5 个定向问题再给带理由的编号选项） | ✅ 采纳进 dream-brainstorm | "先问后议"比直接给方案更能暴露真实需求 |
| Product-Manager-Skills：problem-framing-canvas、press-release（Working Backwards）、5 Whys | ✅ 采纳为方法库 | 多方法库解决"不同模糊度选不同工具" |
| ProductSpec：意图层结构（problem/hypothesis/scope 三段/AC-1 持久 ID/SM-1 分 committed/provisional/spec_revision） | ✅ 采纳进 dream-spec | 工程 spec 之上补"为什么做"的持久记录；持久 ID 让证据可挂靠 |
| ProductSpec：Decision Trace、Agent Run 回执（防漂移） | ✅ 轻量采纳（决策记录 + spec_revision 递增） | 完整回执机制需要 MCP/CLI，文件化即可覆盖个人/小团队 |
| planning-with-files：三文件计划（task_plan/findings/progress）+ 每轮重注入 + /clear 前 flush | ✅ 采纳进 dream-context | "上下文=RAM，文件=磁盘"是防上下文腐化的核心机制 |
| planning-with-files：会话恢复 catchup 流程（恢复 5 轮 vs 裸 agent 13 轮） | ✅ 采纳 | 实测数据支撑的最有价值的机制之一 |
| pro-workflow：自纠正记忆（纠正一次、终身生效） | ✅ 采纳（文件版 learnings.md） | 不引 SQLite/FTS5 依赖；纯文件规则库已够用 |
| caveman：输出经济（结论先行、删废话、代码逐字节精确） | ✅ 采纳进 dream-context 输出纪律 | token 是成本也是注意力；省输出不省精确 |
| Product-Manager-Skills：Light/Standard/Heavy 三档裁剪 | ✅ 思想采纳 | 所有技能用"红线可跳过项"实现轻档（见 ADR-006） |

### 1.6 验证测试层（来自 Web-Quality + Guard + Waza）

| 上游优势 | 采纳 | 裁剪理由 |
|---|---|---|
| Web-Quality：LCP≤2.5s、INP≤200ms、CLS≤0.1、JS<300KB 预算表、a11y=100 | ✅ 全盘采纳 | 可量化阈值是"验证"而非"感觉"的基石 |
| Guard-Skills：第二遍审查（agent 先干活，guard 在 diff 上复查） | ✅ 采纳 | 窄定位（只查不建）是质量门禁的样板 |
| Guard-Skills：AI 特有失效模式（幻觉 API、硬编码假成功、复制粘贴测试、注释污染） | ✅ 采纳 | 通用 lint 不覆盖 AI 的典型错误，这是差异化的核心 |
| Waza：spec verify（触发器→需求 ID→覆盖网格）、CI 门禁退出码 | ✅ 思想采纳（降级为清单勾选） | 全量 CLI 度量属于 skill 平台方工具；终端用户用检查清单即可 |
| Waza：全新上下文评审（规避自我确认偏差） | ✅ 采纳 | 并入 dream-review 的强制要求 |
| Terraform-Skill：V 模型分层（static→unit→integration→E2E） | ✅ 采纳为通用验证分层模型 | 不止 IaC，任何领域都可按四层组织验证 |

## 2. 核心架构理念

### 2.1 三层架构：规格层 / 纪律层 / 验证层

```
┌─────────────────────────────────────────────────────────────┐
│  规格层（单一事实来源）                                        │
│  specs/  = 现状    changes/  = 提案    archive/ = 历史       │
│  dream-spec 管理变更；dream-architect 记录决策(ADR)           │
├─────────────────────────────────────────────────────────────┤
│  纪律层（流程编排）                                           │
│  dream-plan 拆解任务 → dream-tdd 实现 → dream-debug 排障     │
│  dream-ui 负责界面美学 → dream-review 两阶段评审              │
├─────────────────────────────────────────────────────────────┤
│  验证层（不信任第一次产出）                                    │
│  dream-verify 数值阈值门禁 + guard 第二遍审查                 │
│  评审者永远使用全新上下文，验证者不评审自己                    │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 四大支柱原则

1. **权力反转（Power Inversion）**：代码不再是国王，规格可执行化。维护软件 = 演进规格；重构 = 重写规格重新生成。规格服务于人，代码服务于规格。
2. **证据优于断言（Evidence over Claims）**：任何"完成"声明必须附带证据——测试绿、评审通过、阈值达标、diff 自审。无证据 = 未完成。
3. **第二遍不信任（Second-Pass Distrust）**：AI 第一次产出默认存在系统性偏差（自我确认、幻觉、复制粘贴）。架构上强制第二遍：guard 复查、新上下文评审、反 slop 门。
4. **轻量优先（Lightweight First）**：零运行时依赖（纯 Markdown）、SKILL.md ≤ 200 行、渐进式披露。技能包的价值在知识密度，不在工程复杂度。

### 2.3 渐进式披露（Progressive Disclosure）

遵循 Anthropic Agent Skills 规范：SKILL.md 只写"何时用、怎么用、关键步骤"，
细节（检查清单、阈值表、反模式、模板）全部下沉 `references/`，由模型按需加载。
这样 13 个技能常驻 token 预算 ≈ 一个技能全量展开的代价。

### 2.4 触发机制（三通道）

1. **description 触发**：每个 SKILL.md 的 frontmatter description 用"触发词 + 适用场景"句式（如 "Use when the user wants to create or modify a spec-driven change proposal"），模型按语义自动匹配；
2. **斜杠命令**：`/dream-*` 显式入口，适合确定性工作流；
3. **会话钩子**：`hooks/session-start.md` 在会话启动注入元规则"动手前先查可用技能"，把流程从建议变成纪律（Superpowers 强制触发思想）。

## 3. 关键设计决策记录（ADR）

### ADR-001：为什么不用"一个巨型 SKILL.md"，而拆成 13 个技能
- **理由**：单一巨型提示词会造成（a）token 浪费（无关内容常驻）；（b）触发不精准（描述词无法准确命中具体任务）；（c）难维护。Anthropic 规范与 Anthropic/Superpowers 实践均证明：小技能 + 精准 description + 渐进披露是最优解。
- **替代方案**：单文件全家桶（如 ECC 的巨型提示词）——被否，实测常驻成本高、命中率低。

### ADR-002：为什么规格格式选择 OpenSpec 的 delta，而非 Spec-Kit 的全量文档
- **理由**：delta（ADDED/MODIFIED/REMOVED + Scenario WHEN/THEN）天然支持 brownfield 演进与 diff 评审；Spec-Kit 的全量 spec.md+plan.md+research.md 体系更适合 greenfield 重生成。Dreamskills 定位"演进式开发"，选 delta。
- **补偿**：保留 Spec-Kit 的宪法与复杂度门思想，弥补 delta 缺少治理约束的短板。

### ADR-003：为什么验证层与实现层强制分离
- **理由**：Waza 与 Guard-Skills 的共同教训——让写代码的 agent 自评质量等于没有验证（自我确认偏差）。dream-verify 与 dream-review 要求"全新上下文评审 + 数值阈值 + 勾选证据"，验证者不评审自己写的代码。

### ADR-004（修订版 v2）：UI 数据资产整合策略——全量本地化 + 双检索路径

- **v1 决策**：只采纳 UI UX Pro Max 的规则知识（Markdown 化），放弃 CSV 数据与检索引擎（理由：轻量零依赖）。
- **v2 修订**：全量整合（13 个主 CSV + 22 个技术栈 CSV + 4 个 Python 脚本，共约 1.5MB 资产）。修订理由：用户要求"所有设计要素与功能"统一整合；且 CSV 本身不构成运行时依赖——数据资产对任何宿主都是纯文件。
- **双检索路径设计**：① Python 3 环境 → `scripts/search.py` 原版 BM25 检索（保真上游体验）；② 无 Python → 模型直接 grep/读 CSV（SKILL.md 与 data/README.md 提供字段映射），等效检索由模型语义匹配完成。两条路径保证 opencode/codex 及 14+ 宿主在任何环境下可用。
- **资产与提示词分层**：数据（CSV）是"知识"，SKILL.md/references 是"流程与约束"，检索脚本是"可选加速器"——三层解耦，任一缺失均不阻断其余能力。

### ADR-005：为什么保留人类判断权
- **理由**：BMAD "without handing over judgment"——所有门禁设计为"列出证据 → 请求人确认"，绝不自动放行。AI 是优秀的执行者与提议者，但最终判断权（尤其架构与验收）必须保留给人类。

### ADR-006：为什么用文件而非数据库实现记忆（不引入 SQLite）
- **背景**：pro-workflow 用 SQLite+FTS5 做自纠正记忆，planning-with-files 用 Markdown 三文件做计划持久化。两者实测都有效。
- **决策**：Dreamskills 全部用纯 Markdown 文件（learnings.md、三文件计划）。理由：① 零依赖是 ADR-004 确立的底线，SQLite 会打破"任何宿主可运行"；② 文件可 diff、可评审、可 grep，与规格文件体系一致；③ 个人/小团队场景规则量（数百条内）无需 FTS5 检索，模型语义匹配足够。
- **代价与补偿**：规则量大时检索精度下降；补偿——learnings.md 按主题分节，重注入时只加载相关节。

### ADR-007：为什么意图层并入 dream-spec 而非独立技能
- **背景**：ProductSpec 定位"意图层工件"在工程 spec 上游。
- **决策**：意图结构（problem/hypothesis/scope/AC/SM）并入 dream-spec 的 proposal.md，而非独立技能。理由：意图与规格的生命周期同步（提案→实施→归档），拆开会造成两份文件的同步负担；spec_revision 单版本号即可同时覆盖两者。
- **补偿**：需求**澄清过程**（还不确定要什么时）独立为 dream-brainstorm——过程与工件分离，是这两个上游项目各自最擅长的一半。

## 4. 各技能之间的协作关系

```
用户想法（模糊）
   │
   ▼
/dream-brainstorm ─► 意图简报 brainstorm/<slug>-brief.md（澄清后才继续）
   │
   ▼
/dream-init ──► 创建 specs/ + 项目宪法(constitution.md 轻量 6 条)
   │
   ▼
/dream-spec ──► dream-spec: 提案(proposal.md 含 AC/SM 持久 ID) + delta specs + 任务清单
   │                │ 人审提案（CONFIRM 门）◄──────────────┐
   ▼                ▼                                       │
/dream-build ─► dream-research: 有选型疑点先调研（防幻觉证据） │ 否决则回炉
   │            dream-architect: 需要架构决策时记录 ADR      │
   │            dream-plan: 拆 2-5 分钟任务 + [P] 并行标记    │
   │            dream-tdd: 每任务先写失败测试再实现           │
   │            dream-debug: 失败即触发 4 阶段根因定位        │
   │            dream-ui: 有界面需求时过 40 门反 slop         │
   ▼                                                        │
/dream-verify ─► dream-verify: 性能/可访问性/质量阈值门禁 ─────┤
   │                                                        │
   ▼                                                        │
/dream-review ─► dream-review: 全新上下文两阶段评审 ───────────┘
   │
   ▼
/dream-git ──► Conventional Commits 提交 + 分支收尾
   │
   ▼
/dream-archive ─► dream-spec: delta 合并进 specs/ + 变更归档
   │
   ▼
dream-context（全程护航）：三文件计划每轮重注入、/clear 前 flush、
   纠正沉淀 learnings.md、会话恢复 catchup
```

依赖规则：
- `dream-brainstorm` 是 `dream-spec` 的前置（需求模糊时）；意图简报被 proposal 引用
- `dream-research` 的产出被 `dream-architect` 的 ADR 消费（调研不决策）
- `dream-tdd` 依赖 `dream-plan` 的任务粒度（任务太大 TDD 循环失效）
- `dream-verify` 独立于实现（验证者不评审自己），依赖 `dream-review` 的 diff 输入
- `dream-ui` 的输出必须通过 `dream-verify` 的性能门（美学不与性能对立）
- `dream-git` 是合并前的最后一关（门禁绿才提交）；`dream-context` 横向服务所有技能
- `dream-write-skill` 是元技能，扩展现有技能或新增领域技能都走它

## 5. 版本与演进策略

- 技能语义化版本：SKILL.md frontmatter `metadata.version`；
- 宪法（constitution.md）可修订，但必须注明理由、评审记录、向后兼容评估（承袭 Spec-Kit）；
- 新技能通过 dream-write-skill 创建，必须过"四问"：单一职责？触发词精准？≤200 行？细节下沉 references？
