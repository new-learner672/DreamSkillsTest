# Dreamskills 使用操作说明

## 1. 工作流总览

Dreamskills 设计为**按需触发**：AI 根据任务语义自动加载对应技能，也可用斜杠命令显式驱动。

| 阶段 | 技能 | 斜杠命令 | 产出物 |
|---|---|---|---|
| 澄清 | dream-brainstorm | `/dream-brainstorm` | `brainstorm/<slug>-brief.md` |
| 初始化 | - | `/dream-init` | `specs/` + `constitution.md` |
| 规格 | dream-spec | `/dream-spec <名称>` | `changes/<名称>/proposal.md（含 AC/SM）+ specs/ + tasks.md` |
| 调研 | dream-research | `/dream-research <主题>` | `research/<slug>.md` |
| 架构 | dream-architect | `/dream-architect` | `specs/adr/` 决策记录 |
| 计划 | dream-plan | `/dream-plan` | `changes/<名称>/tasks.md`（细化）+ 三文件 |
| 实现 | dream-tdd | `/dream-build` | 测试 + 实现代码 |
| 排障 | dream-debug | （自动触发） | 根因分析 + 修复 |
| 界面 | dream-ui | `/dream-ui` | 设计系统 + 页面代码 |
| 验证 | dream-verify | `/dream-verify` | 阈值门禁报告 |
| 评审 | dream-review | `/dream-review` | 两阶段评审结论 |
| 提交 | dream-git | `/dream-git` | Conventional Commits 提交 |
| 归档 | dream-spec | `/dream-archive` | delta 合并 + 归档 |
| 全程 | dream-context | `/dream-context` | 三文件计划/纠正记忆/恢复 |

## 2. 典型完整流程（新特性开发）

```
用户："用 Dreamskills 给用户系统加一个暗色主题切换功能"

1. /dream-spec dark-mode
   → AI 生成 proposal.md（为什么做、改什么、影响范围）
   → delta specs（ADDED Requirements + Scenario: WHEN/THEN）
   → 人审提案：CONFIRM 通过才继续

2. /dream-plan
   → 拆解为 2-5 分钟粒度任务：
     [P] 任务1: 定义 ThemeContext 类型与测试
     [P] 任务2: 实现 useTheme hook
     任务3: 接入导航栏切换按钮（依赖 1,2）
     任务4: 持久化 localStorage + 跟随系统偏好
   → [P] 标记可并行任务

3. /dream-build（逐任务执行）
   → 每任务：先写失败测试 → 看它失败 → 最小实现 → 看它变绿 → 重构
   → 实现过程中若有界面改动，自动过 dream-ui 的 40 门反 slop 清单
   → 失败即触发 dream-debug 的 4 阶段根因定位

4. /dream-verify
   → 性能门：LCP≤2.5s / INP≤200ms / CLS≤0.1 / JS 包 <300KB
   → 可访问性：WCAG 2.2 抽查 + 对比度 4.5:1 + reduced-motion
   → guard 第二遍审查：幻觉 API、硬编码假成功、复制粘贴测试
   → 逐项勾选证据，未达标回炉

5. /dream-review
   → 阶段一：代码是否忠实实现规格（对照 delta specs 的 Scenario）
   → 阶段二：代码质量（SOLID/复杂度/命名）
   → 评审者用全新上下文，不参考实现者的自述

6. /dream-archive dark-mode
   → delta specs 合并进 specs/，变更移入 archive/2026-08-13-dark-mode/
```

## 3. 各技能操作详解

### 3.1 dream-spec（规格驱动）

触发词：创建变更、新功能提案、修改需求、归档。

- `/dream-spec <名称>`：创建 `changes/<名称>/`（proposal.md + specs/ + tasks.md）
- 关键规则：歧义必须写 `[NEEDS CLARIFICATION: 问题]`，禁止猜测；只写 WHAT/WHY 不写 HOW
- 人审门：提案须经用户 CONFIRM 才进入实施
- `/dream-archive <名称>`：delta 合并进 `specs/`，变更归档

### 3.2 dream-architect（架构设计）

触发词：技术选型、系统设计、重构方案、需要架构决策。

- 产出：`specs/adr/NNNN-标题.md`（决策记录：背景/选项/决策/后果）
- 复杂度门：引入每个新抽象必须回答"为什么现在需要"，理由不足则拒绝（反过度设计）
- 宪法约束：库优先（可复用逻辑先做成独立模块）、测试先行、反抽象（≤3 层）

### 3.3 dream-plan（计划拆解）

触发词：拆任务、做计划、规划实现步骤。

- 粒度：每个任务 2-5 分钟可完成、可独立验证
- 依赖：显式声明依赖链；无依赖任务标 `[P]` 可并行
- 输出写入 `tasks.md`，完成后勾选（不依赖 MCP，纯文件状态）

### 3.4 dream-tdd（测试驱动开发）

触发词：实现功能、写代码、修复缺陷。

- 铁律：先写失败测试 → 确认失败（红色）→ 最小实现（绿色）→ 重构（保持绿色）
- 反模式 12 条：mock 自己的被测对象、测试复读实现逻辑、删掉"抓不到任何东西"的测试等
- 禁止"顺带修复"：每循环只解决当前任务

### 3.5 dream-debug（系统化调试）

触发词：报错、不工作、测试失败、行为异常。

- 4 阶段：复现（稳定触发）→ 定位（二分缩小到根因）→ 修复（最小改动）→ 验证（回归通过）
- 红线：根因未确认前禁止动手改代码；修复后必须写出"证据链"（现象→根因→修复→验证）

### 3.6 dream-ui（UI/UX 全谱系设计）

触发词：设计页面、美化界面、UI 需求、配色、字体、图标、Logo、横幅、幻灯片、品牌、设计系统、设计审计。

- **设计任务路由**：先分流——页面/组件走主流程；Logo/横幅/图标/品牌/token/slides/审计走对应 references（`design-routing.md`/`brand-guide.md`/`design-tokens.md`/`stack-guides.md`/`audit-guide.md`）
- **主流程 6 步**：① 分析需求（产品类型 + **技术栈检测**，绝不假设）→ ② 生成设计系统（检索脚本或 CSV 直读，双路径）→ ③ 补充细化检索 → ④ macrostructure 先行 + 实现 → ⑤ 过 40 门反 slop 清单 → ⑥ 7 阶段设计审计
- **设计滑杆**：`DESIGN_VARIANCE / MOTION_INTENSITY / VISUAL_DENSITY`（1-10），与检索脚本 `--variance/--motion/--density` 语义一致
- **数据资产**：84 风格/192 产品/192 配色/74 字体/161 推理规则/98 UX 指南/22 技术栈（`data/*.csv`）；有 Python 3 用 `scripts/search.py` BM25 检索，无 Python 直接 grep/读 CSV
- **持久化**：`--persist` 生成 `design-system/<项目>/MASTER.md`（唯一事实源）+ `pages/` 页面级覆盖；MASTER 已存在默认不覆盖
- **0 结果禁止编造**：换词重试一次 → 仍空则用内置默认并明确告知用户
- **硬规则**：禁 em-dash 破折号、禁 emoji 当图标、对比度 4.5:1、hover 150-250ms、reduced-motion、响应式断点、禁 AI 紫粉渐变（金融/企业）
- **子能力**：Logo（白底输出）、CIP 全套物料、图标（7 风格参数 SVG）、横幅（平台尺寸表）、社媒图（8 步编排）、幻灯片（Chart.js + 文案公式 + Pattern Breaking）

### 3.7 dream-verify（验证测试）

触发词：检查质量、性能优化、验收、测试覆盖率。

- 四层验证（V 模型）：静态检查 → 单元 → 集成 → E2E
- 数值门禁：性能（CWV 阈值 + 预算表）、可访问性（WCAG 2.2）、SEO、安全头
- guard 复查：AI 特有失效模式清单（幻觉 API/假成功/复制粘贴/注释污染）
- 输出：逐项勾选的门禁报告，任何红灯阻断合入

### 3.8 dream-review（代码评审）

触发词：评审、review、合并前检查。

- 两阶段：① 规格符合性（对照 Scenario 逐条核对）② 代码质量（SOLID/复杂度/命名/边界）
- 硬约束：评审者用全新上下文启动，不读实现者的自我总结；每个问题必须给出"证据位置"（文件:行号）

### 3.9 dream-write-skill（元技能）

触发词：写一个新技能、扩展 Dreamskills。

- 规范：SKILL.md 主体 ≤200 行；frontmatter 含 name/description（触发词式描述）；细节下沉 references/
- 四问：单一职责？触发词精准？≤200 行？细节下沉？
- 产出：新技能目录 + 在 README 映射表注册

### 3.10 dream-brainstorm（需求探索）

触发词：想法模糊、需求澄清、"帮我看看这个想法"、要不要做。

- 流程：倾听复述 → Adaptive Decision Ladder（一次问 3-5 个定向问题）→ 编号方案（带"何时选它"理由）→ 收敛意图简报
- 意图简报：problem / hypothesis / scope（In-Out-Cut 三段）/ AC-1 持久编号 / SM-1（committed/provisional）/ OQ-1 开放问题
- 方法库：问题框架画布、press-release 法、5 Whys、反方案
- 输出是 dream-spec 的直接输入

### 3.11 dream-research（调研）

触发词：技术选型、调研、对比库、查资料。

- 六阶段：定义 RQ → 收集 → 筛选 → 分析（对比矩阵）→ 合成 → 落盘 `research/<slug>.md`
- 防幻觉纪律：每条结论附来源；不确定标 `[未证实]`；禁止编造 API/版本/benchmark
- 调研不决策——产出供 dream-architect 的 ADR 消费

### 3.12 dream-git（Git 纪律）

触发词：提交、commit、分支、合并。

- 一个变更一个分支（feat/fix/refactor 前缀）；并行用 worktree 隔离
- 提交规范：`type(scope): subject`（subject ≤50 字符），一个提交一件事，body 写"为什么"
- 提交前自检：git status 无意外文件 → diff --check → 只暂存相关文件
- 合并前必过 dream-verify + dream-review 门禁；合并后删分支

### 3.13 dream-context（上下文持久化）

触发词：恢复会话、继续上次、记住教训、/clear 前。

- 三文件计划：task_plan.md（阶段+复选框）/ findings.md（决策追加）/ progress.md（日志+错误）
- 每轮重注入计划浓缩块（目标/下一步/当前阶段/最近 3 决策），防上下文腐化
- 会话恢复：读三文件 → catchup 摘要（≤10 行）→ 用户确认后继续
- 纠正沉淀：用户纠正 → 问是否入 `.dreamskills/learnings.md` → 每轮自动加载相关规则
- 输出经济：结论先行、删废话、代码/命令/报错逐字节精确

## 4. 常见问题

**Q：必须走完整流水线吗？**
A：不必。小改动可直接 `/dream-build`，跳过 spec/plan；但 verify/review 不可跳过（第二遍不信任原则）。

**Q：已有项目（brownfield）能用吗？**
A：能。dream-spec 的 delta 格式就是为演进式变更设计的；初始化时把现状写成 specs/ 基线即可。

**Q：和现有 OpenSpec 技能（.opencode/skills/openspec-*）冲突吗？**
A：不冲突。Dreamskills 的 dream-spec 是独立实现；若已用 OpenSpec，可只用 dream-ui/dream-verify/dream-review 等其余技能。

**Q：token 消耗大吗？**
A：13 个 SKILL.md 主体合计约 2000 行，常驻描述只有 13 段 frontmatter；细节按需加载，代价与单个全量技能相当。
