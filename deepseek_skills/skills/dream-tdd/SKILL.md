# 测试驱动开发（dream-tdd）

> 定位：写任何有逻辑的代码前，先用失败测试锁定行为——红-绿-重构是默认路径，不是可选建议。
> 吸收思想：superpowers 的 TDD loop（强制红-绿-重构）+ anthropics 官方 TDD（限制单次变更规模）+ mattpocock tdd（TDD 先行、轻量注入）。

## 何时使用（触发条件）

- 实现业务逻辑、算法、接口、数据层、工具函数之前；
- 修复 bug 后补回归测试（dream-debug 的下游）；
- 重构前先补特性测试（锁定行为再重构）；
- 用户说"用 TDD 实现""先写测试"。

不适用：纯 UI 布局/样式微调（无逻辑，走 dream-design-system / dream-ui-polish）；E2E 场景验证（归 dream-webapp-test）；light 模式下可豁免（可选）。

## 核心原则

1. **红-绿-重构，顺序不可颠倒**：先写失败测试并确认失败（红）→ 最小实现通过（绿）→ 重构（行为不变）；**禁止先实现后补测试**。
2. **最小实现**：绿阶段只写让测试通过的最少代码，不做"顺便优化"。
3. **测试粒度分层**：单元测试优先（函数/类）→ 接口/集成测试次之 → E2E 归 dream-webapp-test（浏览器级）。
4. **覆盖分级**（依 `.dreamspec/SKILLS.md`）：rigorous 全量覆盖（含边界与异常）；balanced 覆盖核心路径（happy path + 关键异常）；light 可选（至少冒烟）。
5. **一个失败测试一次修复**：限制单次变更规模，失败面小、定位快（anthropics 思想）。
6. **测试也是代码**：测试要可读、无坏味道（见 references/test-smells.md），测试坏掉一样要修。

## 工作流程

### 步骤 1：确定测试范围（输入）

- 读取任务/验收点（tasks.md 或 spec-delta 的 GWT）；
- 按强度模式确定覆盖级别（rigorous 全量 / balanced 核心路径 / light 可选）；
- 确定粒度：单元（函数级）还是接口（API/集成级）。

### 步骤 2：红 —— 写失败测试（动作）

- 先写一个失败测试（一个行为一个测试）；
- 运行测试，**确认失败且失败原因正确**（如"预期通过但抛错"→ 说明测试有效）；
- 失败原因不对（如测试本身写错）→ 修测试，不进入实现。

### 步骤 3：绿 —— 最小实现（动作）

- 写让该测试通过的最小代码；
- 运行测试全绿，且没有破坏其他测试。

### 步骤 4：重构（动作）

- 在测试全绿的保护下重构（消除重复、改善命名、调整结构）；
- 每步重构后跑测试，保持全绿；行为不变是底线。

### 步骤 5：记录证据（产物）

- 记录三态证据：红（失败输出）→ 绿（通过输出）→ 重构（仍通过）；
- 写入块验证记录（供 dream-verify 取证）。

## 验收标准

- [ ] 先写失败测试并确认失败（红），非先实现后补测试
- [ ] 最小实现通过（绿），无多余代码
- [ ] 重构后测试仍全绿，行为不变
- [ ] 覆盖分级符合强度模式（rigorous 全量 / balanced 核心 / light 可选）
- [ ] 粒度合理：单元优先，E2E 已移交 dream-webapp-test
- [ ] 测试无坏味道（对照 references/test-smells.md）

## 与其他技能的衔接

- 上游：dream-spec-implement / dream-execute（逻辑块的护航技能）、dream-debug（修复后补回归测试）、dream-plan（重构前先补特性测试）
- 下游：dream-git（提交）、dream-verify（验证门证据）
- 并行：E2E 场景归 dream-webapp-test；性能断言归 dream-perf-audit
- 强度模式：light 可选（至少冒烟）；balanced 核心路径；rigorous 全量含边界异常
