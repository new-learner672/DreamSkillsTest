# 红-绿-重构循环细则与误区（references）

> 本文件由 dream-tdd 按需加载。细化 TDD 循环的每一步，列出最常见误区。

## 1. 循环细则

### 红阶段（写失败测试）

1. 从验收点/GWT 中提取**一个**具体行为（一个测试只锁一个行为）；
2. 测试命名描述行为而非实现（`should_reject_wrong_password` 而非 `test_login_2`）；
3. 运行测试确认**失败**，且失败原因符合预期：
   - 失败 = "实现缺失/行为不符" → 测试有效，进入绿阶段；
   - 失败 = "测试本身写错/环境问题" → 修测试，不写实现；
4. 该阶段禁止写实现代码（连"先写一半实现"都不行）。

### 绿阶段（最小实现）

1. 只写让当前测试通过的最少代码——临时写法、硬编码返回值都允许（仅限本阶段）；
2. 跑全量相关测试：目标测试通过、其他测试不破坏；
3. 若测试需要多步实现，可拆小步（每步仍先红后绿）。

### 重构阶段（行为不变）

1. 测试全绿是重构的前提；
2. 只做不改变行为的改动：消除重复、改善命名、抽取函数、调整分层；
3. 每完成一次小重构就跑一次测试；
4. 重构后仍全绿才算完成；发现行为变化 → 回退该步重构。

## 2. 常见误区（对照检查）

| 误区 | 表现 | 正确做法 |
|---|---|---|
| 先实现后补测试 | "功能写完了，补个测试记录一下" | 这是测试记录不是 TDD；先写失败测试 |
| 红阶段写实现 | 测试和实现一起写 | 严格先红后绿 |
| 绿阶段过度实现 | 顺手把下一步功能也写了 | 最小实现，只过当前测试 |
| 重构顺带改行为 | "重构时顺便改了返回值" | 重构=行为不变；行为改动单独走红绿 |
| 测试过大 | 一个测试测整个流程 | 一个测试一个行为 |
| 跳过重构 | 绿了就提交，代码重复严重 | 重构是第三步，不可省略 |
| 测试依赖实现细节 | 改实现就改测试 | 测试测行为不测实现 |
| 忽略失败原因 | "反正红了就对了" | 确认失败原因正确（行为不符 vs 测试写错） |

## 3. 边界情况

- **无逻辑代码**（纯样式/静态内容）：不需要 TDD，直接走设计层技能；
- **已有代码补测试**：先写特性测试锁定现状（可能先红），再重构（重构场景的标准路径）；
- **测试难写**（依赖 IO/时间）：用依赖注入、抽象时钟、mock 边界——不要为了"能测"把测试写成空壳；
- **E2E 场景**：不在本技能范围，交给 dream-webapp-test（真实浏览器）。

## 4. 三态证据记录模板

```markdown
块 N 验证记录（TDD）
- 红：`npm test` → 1 failed（should_reject_wrong_password）失败原因符合预期
- 绿：`npm test` → 1 passed（最小实现：校验密码哈希）
- 重构：提取 validateCredentials() 后 → 全量测试仍通过
```
