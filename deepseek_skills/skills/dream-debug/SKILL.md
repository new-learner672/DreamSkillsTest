# 系统化调试（dream-debug）

> 定位：用科学方法定位根因——复现、二分、根因、修复、回归，杜绝"瞎猜改症状"。
> 吸收思想：superpowers 的 systematic-debugging（复现→隔离→修复→验证）+ mattpocock debugging（先复现再猜根因）。

## 何时使用（触发条件）

- 程序报错、行为不符合 spec/GWT、测试失败；
- 用户说"系统化调试""帮我查 bug""定位问题"；
- 实施（dream-spec-implement / dream-execute）过程中遇到异常行为。

不适用：性能问题（走 dream-perf-audit）；安全问题（走 dream-security-check）；需求本身不清（回 dream-brainstorm）；已知根因的直接修复（无需完整调试流程）。

## 核心原则

1. **先复现，再动手**：无法稳定复现的问题不要开始改代码——复现是调试的地基。
2. **二分缩小范围**：用二分法（改一半/断点/最小复现）快速收敛到可疑代码段，而非逐行排查。
3. **定位根因，不是改症状**：修复必须指向根因；只改表面症状（如"加个 try-catch 吞掉错误"）是反模式。
4. **证据链**：每个结论都要有证据（日志、堆栈、数据、最小复现用例），不凭直觉。
5. **修复后回归验证 + 补测试**：修复通过后补回归测试（dream-tdd），防止复发。

## 工作流程

### 步骤 1：复现（输入/动作）

- 拿到触发条件（输入、步骤、环境）；
- 构造**最小复现**：去掉无关因素，留下能稳定触发的最少步骤/用例；
- 记录复现输出（错误信息、堆栈、异常数据）。

### 步骤 2：二分缩小（动作）

- 按 references/bisection-playbook.md 的方法（前端/后端/环境/并发分类），用二分法缩小可疑范围：
  - 数据层/逻辑层/展示层，哪一层出的问题？（层层排除）
  - 用断点、日志插桩、git bisect（回归引入点）辅助定位；
- 每缩小一次就验证一次（问题是否还在），确保方向正确。

### 步骤 3：定位根因（动作）

- 找到根因：明确"哪一行/哪个逻辑/哪个状态导致了问题"；
- 验证根因：**在根因处做最小修改后问题消失**（证明根因正确）；
- 记录根因报告要素：现象 → 最小复现 → 根因 → 证据。

### 步骤 4：修复（动作）

- 最小改动修复根因（不顺手改无关代码）；
- 修复后重跑最小复现，确认问题消失且无副作用。

### 步骤 5：回归验证与补测试（产物）

- 跑相关全量测试/构建，确认无回归；
- 用 dream-tdd 补一条回归测试（覆盖此 bug 的场景），防止复发；
- 用 dream-git 提交（提交信息含根因摘要）。

### 步骤 6：根因报告（产物）

- 输出根因报告（写入块验证记录或会话摘要）：
  `现象 → 最小复现 → 二分过程 → 根因 → 修复 → 回归测试`。

## 验收标准

- [ ] 已稳定复现（有最小复现用例），非"猜测式"调试
- [ ] 通过二分缩小范围，有证据链（日志/堆栈/测试）
- [ ] 根因已定位并验证（修改根因后问题消失）
- [ ] 修复为最小改动，未顺手改动无关代码
- [ ] 回归验证通过，且已补回归测试（dream-tdd）
- [ ] 根因报告已产出

## 与其他技能的衔接

- 上游：dream-spec-implement / dream-execute（实施遇错时挂载）、任何技能遇到 bug 时
- 下游：dream-tdd（补回归测试）、dream-git（提交修复）、dream-verify（验证门）
- 并行：性能类问题转 dream-perf-audit；安全类问题转 dream-security-check
- 强度模式：light 可简化二分过程（直接定位修复）；rigorous 要求完整根因报告与回归测试
