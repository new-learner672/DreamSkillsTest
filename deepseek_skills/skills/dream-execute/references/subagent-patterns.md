# 子代理委派模式（references）

> 本文件由 dream-execute 按需加载。定义"何时委派、怎么委派、角色模板、何时绝不委派"。

## 1. 委派 vs 单代理：判定标准

| 信号 | 委派（推荐） | 单代理顺序执行（默认） |
|---|---|---|
| 块规模 | 复杂、多文件、跨层 | 小而直白 |
| 领域跨度 | 前后端/多技术栈同时出现 | 单一技术栈 |
| 并行性 | 多块无依赖可并行 | 强依赖链 |
| 上下文压力 | 单块内容已接近上下文上限 | 上下文充足 |
| token 预算 | 预算充足、可接受多代理开销 | 预算敏感（默认省 token） |

**默认单代理顺序执行**；只有当上述"委派"列命中 3 项以上才考虑委派。

## 2. 委派流程（主代理编排）

1. **拆块**：从 tasks.md 取委派块，拆成子代理可独立完成的子任务（每子任务带明确输入/产物/验收点）；
2. **派单**：给每个子代理发独立任务（含上下文：spec-delta 相关 GWT、DESIGN.md tokens、验收点、产出路径）；
3. **收单**：子代理返回代码/测试/报告；
4. **整合与验证**：主代理必须亲自做块级验证（测试/构建/检查 diff），不合格退回重做——**主代理对质量负全责**；
5. **提交**：整合后由主代理做原子提交（dream-git），勾选 tasks.md。

## 3. 角色模板

| 角色 | 职责 | 验收点示例 |
|---|---|---|
| frontend | UI 组件、页面、交互；遵循 DESIGN.md tokens | E2E 关键流程通过、反 slop 自检通过 |
| backend | 接口、数据层、业务逻辑；先写失败测试 | 接口测试通过、无未处理异常 |
| tester | 补测试、跑回归、找边界用例 | 覆盖 GWT 全部场景、无回归 |
| reviewer | 审查代码质量、安全、可维护性（类似 dream-review 前置） | 问题分级清单，阻断项清零 |

> 角色定义参考 VoltAgent/wshobson 的"单职责子代理"思想；角色是**任务边界**，不是永久人格。

## 4. 适用 / 不适用场景

**适用**：
- 跨前后端的完整功能（frontend + backend 并行）；
- 独立模块批量实现（如多个无依赖的 CRUD）；
- 需要长上下文的大块（拆开避免上下文溢出）；
- 测试/审查等相对独立的辅助任务。

**不适用（绝不委派）**：
- 小任务（委派开销 > 收益）；
- 强依赖、必须顺序完成的块；
- 需要频繁与用户交互决策的任务（子代理无法替用户拍板）；
- 子代理产出无法验证的任务（不可验证 = 不可委派）。

## 5. 常见反模式

- ❌ 委派后不验证直接合入——"甩锅式交付"；
- ❌ 把需要用户决策的块丢给子代理——产品决策必须回到主会话；
- ❌ 每个块都委派——token 浪费与角色僵化（superpowers 被诟病的点）；
- ✅ 委派前写清楚子任务的验收点，收单后主代理按验收点验证。
