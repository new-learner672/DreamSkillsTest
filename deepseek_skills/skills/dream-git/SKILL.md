# 提交与分支纪律（dream-git）

> 定位：让每次提交都是一个可独立验证、可单独回滚的原子单元——git 历史即实施轨迹。
> 吸收思想：工程最佳实践（原子提交、小步提交）+ superpowers 的 git workflow（提交纪律内建于流程）。

## 何时使用（触发条件）

- 完成 tasks.md 中一个逻辑块（dream-spec-implement / dream-execute 每块完成后）；
- 修复一个 bug 后（dream-debug 完成后）；
- 用户说"提交代码""原子提交""commit 这一块"。

不适用：块级验证未通过时（先修复再提交）；临时调试代码/未完成的工作（除非用 WIP 分支明确标注）。

## 核心原则

1. **原子提交**：一个逻辑块 = 一次提交；提交内不混入无关变更（如"顺手改的格式"）。
2. **提交信息约定**：`<块号>: <意图> - <摘要>`（如 `001块2: 实现登录接口 - 校验密码并签发会话`）；根因修复类含根因摘要。
3. **小步提交、可单独回滚**：提交粒度小到能单独回滚而不牵连其他功能。
4. **验证先行**：**禁止提交未通过块级验证的代码**（测试/构建/冒烟通过才提交）。
5. **分支策略遵循项目约定**：读 CLAUDE.md 的分支与 PR 流程（trunk-based / feature branch / PR review），Dreamskills 不引入新分支规范。

## 工作流程

### 步骤 1：确认验证通过（输入）

- 确认本块块级验证通过（dream-tdd 测试绿 / 构建成功 / 冒烟通过）；
- 验证未通过 → 回到实现/调试，不进入提交。

### 步骤 2：检查 diff（动作）

- `git status` / `git diff`：确认变更只属于本块；
- 发现无关变更（别的块的文件、临时调试代码、生成物）→ 从暂存区剔除（`git add` 只加本块文件）。

### 步骤 3：原子提交（动作）

- 按约定写提交信息：`<块号>: <意图> - <摘要>`（模板见 references/commit-conventions.md）；
- 一个逻辑块一次 commit；若本块涉及多个独立小步，可拆多个小提交（仍属本块范围）。

### 步骤 4：分支管理（动作）

- 遵循 CLAUDE.md 的分支约定（创建 feature 分支 / 直接 trunk）；
- 若项目有 PR 流程：提交后推分支并提示用户走 PR review。

### 步骤 5：记录（产物）

- 在 tasks.md 对应块勾选旁记录提交哈希（`- 提交：abc1234`），保持"块 ↔ 提交"可追溯。

## 验收标准

- [ ] 提交前块级验证已通过（禁止未验证提交）
- [ ] 一次提交只含一个逻辑块，无无关变更
- [ ] 提交信息符合约定（块号 + 意图 + 摘要）
- [ ] 提交粒度可单独回滚（小步提交）
- [ ] 分支策略遵循 CLAUDE.md 项目约定
- [ ] tasks.md 记录了提交哈希

## 与其他技能的衔接

- 上游：dream-spec-implement / dream-execute（每块完成后）、dream-debug（修复后）、dream-tdd（测试代码随块提交）
- 下游：dream-review（审查提交/PR）、dream-verify（验证门）
- 并行：分支与 PR 流程遵循 CLAUDE.md 约定（不另行定义）
- 强度模式：light 可简化为整块一次提交；rigorous 要求严格原子提交 + 每块提交哈希登记
