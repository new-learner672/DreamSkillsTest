# 需求澄清头脑风暴（dream-brainstorm）

> 定位：实施前把含糊的需求问清楚——追问边界、规则、异常与优先级，让 spec 建立在共识之上。
> 吸收思想：superpowers 的 brainstorming（先质疑需求再动手，不急于产出）。

## 何时使用（触发条件）

- 需求有歧义：边界不清、规则缺失、异常未定义、优先级不明；
- 重大决策前：技术选型、接口设计、影响面大的改动；
- 用户说"帮我理清需求""brainstorm 一下"；
- 提案（dream-spec-propose）或计划（dream-plan）中发现缺口需要补问。

不适用：需求已清晰无歧义（不要为问而问）；light 模式可跳过，直接进入 plan。

## 核心原则

1. **一次只问最关键的问题**：连环追问不是一次抛出 20 个问题，而是每轮 1~3 个最影响决策的问题，等回答再继续。
2. **问边界、问规则、问异常、问优先级、问非目标**：五个维度是澄清的主干（详见 references/question-bank.md）。
3. **不替用户做产品决策**：澄清是帮用户想清楚，不是替用户拍板；拿不准的优先级/取舍必须交给用户。
4. **结论必须落盘**：澄清结果写入提案背景或 tasks.md 头部，成为 dream-plan 与实施的依据（工件即记忆）。
5. **及时收敛**：问题足够支撑提案/计划就停止，不无限追问（防止"过度工程"式澄清）。

## 工作流程

### 步骤 1：识别含糊点（输入）

- 读取需求原文 / proposal.md / spec-delta.md；
- 列出含糊点：哪些句子无法转成可验证的 GWT？哪些"默认行为"没有说明？

### 步骤 2：逐轮追问（动作）

- 每轮从 references/question-bank.md 中按维度挑选**最关键的 1~3 个问题**提问；
- 追问顺序建议：边界 → 规则 → 异常 → 优先级 → 非目标；
- 根据回答继续深挖（如"密码强度规则"→"是否允许特殊字符？"），直到该维度清晰。

### 步骤 3：记录结论（产物）

- 把澄清结论写入**提案背景**（若有提案）或 **tasks.md 头部"澄清结论"小节**；
- 格式：`- 决策：<问题> → <结论>（用户确认）`，可标注来源（用户原话/推断需标注）。

### 步骤 4：复述确认（动作）

- 用一段话复述最终理解（含边界、非目标、关键规则）；
- 请用户确认；确认后返回 dream-spec-propose（补全提案）或 dream-plan（进入计划）。

## 验收标准

- [ ] 边界（做什么/不做什么）已明确
- [ ] 关键规则与异常行为已定义（可转成 GWT）
- [ ] 优先级与非目标已记录
- [ ] 结论已落盘（提案背景或 tasks.md 头部），非只存在于对话
- [ ] 未替用户做产品决策（决策人=用户）

## 与其他技能的衔接

- 上游：dream-spec-propose（提案中含含糊需求时挂载）、需求输入
- 下游：dream-spec-propose（补全提案背景）、dream-plan（澄清结论进入 tasks.md 头部）
- 强度模式：light 可跳过；rigorous 下澄清必须落盘且逐条确认
